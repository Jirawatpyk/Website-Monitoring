# packages/engine

The status engine as pure functions: no I/O, no clock (`now` is always a parameter), no database. The cron route loads state, calls these, and writes the result.

- `round.ts` — DOWN rule (spec §6): ≥ 2 of 3 locations hard-fail on two checks in a row; blocked → browser verifier; faulty-location exclusion (spec §15.3); regional PROBLEM.
- `lifecycle.ts` — incident states and events (spec §15.4), the 3-condition resolve gate (§16.2–3), client-update track (§9, §16.2), PROBLEM auto-resolve (§16.1).
- `monitor.ts` — one engine step per primary monitor (S02a): rounds are interval buckets (`floor(checkedAt / interval)`), judged oldest first, once each (`roundAt` = bucket start), when every active location reported and every failure was rechecked, or `ROUND_DEADLINE_MS` after the round ends; DOWN needs both checks hard-failing (rechecks only vote in the second) and starts at the first failed check (walking back through consecutive failures); an OK round needs a majority of reporting locations to pass; recover → Monitoring on the first OK round, settle on the second. Staging cron offsets (probe-tyo :02, probe-sin :46, engine :39) are in its tests.
- Blocked rounds (S03, D-001, D-019, D-020): a round with no pass or hard-fail majority and a blocked location asks the runner for a verify job (`verify`), waits while it runs, then — loaded → an OK round with `BLOCKED_NOTE`; failed → DOWN from the first blocked check (`verifyJobId`); blocked in the browser too, or the verifier unavailable (no poll 2 min, not picked up in 30 s, lease ran out) → `unverified` (PROBLEM, note `UNVERIFIED_NOTE`). Hard fails never wait for the verifier: a later round that confirms DOWN is judged past a blocked round still waiting for its verdict. A round where two locations failed the check and the recheck is judged without waiting for the third. A DOWN confirmed while the open incident is a PROBLEM is `escalate` (D-021). Every judged decision carries the site's `note` (none clears it).
- `site.ts` (S04a, D-022) — `decideSite`, the step the runner calls: every monitor of a site judged on the same round, each to a verdict (OK, PROBLEM with its trigger and `ProblemDetail`, or — the primary only — DOWN; a key page caps at PROBLEM `key_page`). Site status = the worst verdict, never below an unrecovered incident's severity (S03 M1: a blocked round the verifier can't decide while the incident is in Monitoring shows PROBLEM, the next OK round shows OK); an incident recovers on the first round every monitor is OK. Carry state between rounds (`MonitorCarry`: slow streak, per-location failing-since, last verdict) comes from `monitor_status` and goes back in each decision's `monitors`. `decideMonitor` is the one-primary-monitor view kept for the S02a / S03 round tests.
- `triggers.ts` (S04a) — the PROBLEM triggers as pure rules: slow (p50 of passing checks over the limit 3 rounds in a row), keyword (majority of the locations that checked), redirect (majority ending outside the monitor's base host / allowlist), key page 4xx, regional (one location failing ≥ 5 min while the round passes), faulty location per probe minute (`faultyLocations`, only with ≥ 3 monitors from that location).
- `uptime.ts` — 1 − DOWN minutes / (window − maintenance), time-weighted across sites (spec §5).
- S04b (D-004, D-023, D-024; spec §19.3–19.7): a new DOWN / PROBLEM on a recovered incident is `relapse` (DOWN AGAIN / PROBLEM AGAIN; a DOWN on a recovered PROBLEM incident stays `escalate`, D-021). Recovery and the status floor follow `episodeSeverity`: a DOWN drop ends when the home page answers again (D-023, `recover` with `allOk: false` and `then` = the PROBLEM AGAIN from the same round), a PROBLEM drop when every monitor is OK. Flapping: `isFlapping(flips, flipOk, at)` — flips are OK ↔ not-OK changes at incident steps, kept by the SQL functions; a flapping incident's `recover` has `holdSummary`. `recover.autoResolve`: a PROBLEM nobody acknowledged, cleared < 5 min after it was flagged (`detectedAt`, §19.6). `relapseState`, `episodesOf` (the drops of an incident) in `lifecycle.ts`; `outageMinutes` / `settledOutageMinutes` (D-033: how long it was down — DOWN drops only for a DOWN incident, whole clock minutes, VOCA 41 min — the one number every page, MTTR and message uses); the VOCA timeline end to end in `relapse.test.ts`.

- S05b (D-027): on a site flagged `behindWaf`, `evaluateRound({ wafSite })` lets a WAF-signed block (`waf` set) and a Bangkok result whose control check failed (`controlOk: false`) sit the round out (`abstainsOnWafSite`); the locations left decide and one is enough — a pass → OK with `wafNote` ("Verified from BKK; SIN, TYO blocked by bot protection"), a hard fail confirmed by that location's recheck (`minReporting: 1`) → DOWN; nothing left and the control down → `untrusted` → PROBLEM (unverified, `control_failed`), never DOWN; everyone WAF-blocked → the verifier as before. The trigger rules (`roundP50`, `keywordIssue`, `redirectIssue`, `statusIssue`) take `min` 1 for such a one-location round. Sites without the flag are untouched; the cases are in `waf.test.ts`. When a location really sat out (`wafRound` in `judgeMonitor`) the voters' verdict stands: one passing voter makes an OK round, its keyword / redirect / slow / key-page evidence counts (`min` 1), `regionalIssue(…, true)` judges the one failing; an abstaining location's failing-since clock restarts. The control check is read before the faulty-location exclusion and outranks the verifier (same VPS): nobody left + control down → `untrusted`, also on the recheck. The WAF note comes from the home page only. Rule 2b: `bkkUntrusted(r, akamaiSite)` also sits out a BKK failure whose Akamai control (`akamaiOk: false`) failed on a site whose checks carry `waf: 'akamai'`; rule 2c: the DOWN's start walks back only through failures the controls vouched for; a WAF DOWN carries `wafBlocked` for "Confirmed by" (`formatConfirmedBy` in `@dxt/shared`). D-028: `bkkControlFailing` (`control.ts`) says whether the BKK control check failed its last 3 probe minutes — the runner's Admin alert. D-038: `SiteSnapshot.bkkControlDown` (the runner: `bkkControlDown` over every BKK batch — a minute fails when any batch failed the control, 3 such minutes in a row; the open alert only with no control reported or no passing minute) gates the `untrusted` → PROBLEM step; without it such a round is `insufficient` — no data, the status and OK-round count hold. D-039: `slowLocationsByMinute` (`triggers.ts`) — the only location over 3 s (`SLOW_LOCATION_MS`, or a site's own lower limit) on more than half of its 3+ timed sites in a minute, and so on 3+ sites another location timed while that one wasn't — goes to `SiteSnapshot.slowLocations`; `judgeMonitor` leaves its times out of the round's p50 (only the slow rule; an open slow PROBLEM holds), so the Bangkok VPS slowing down never makes a WAF site slow. `SiteSnapshot.bkkControlDown` may be a function of the round's time and whether the site is behind Akamai; a D-038 no-data round resets the slow streak. The runner reports recent slow-location minutes in its summary (`slowLocations`, logged with the run).
- D-029: `isHardFail(check)` (`hard-fail.ts`) is the one rule for a hard-fail vote — a certificate-chain error (`isTlsChainError`) never counts toward DOWN, regional or faulty; ESLint refuses `outcome === 'fail'` elsewhere in `src`. Chain errors at a majority of the reporting locations → PROBLEM `tls_chain` in one round (`judgeMonitor`, after the hard-fail branch); cases in `tls-chain.test.ts`.

- S08 (D-034): `response-hours.ts` — Tier 2–3 minutes inside Mon–Fri 09:00–18:00 Bangkok minus company holidays (`isInsideHours`, `nextOpening`, `addInsideMinutes`, `minutesInsideHours`; [start, end)). `escalation.ts` — `ladderDue` (the next level once its time came, the latest reminder due, `pausedUntil`), `scheduleOf`, `problemHoldUntil`: the clock starts at Confirmed down, Tier 1 24/7, Tier 2–3 in response-hours minutes, only while Unacked / Escalated, one level per call, a reminder every `reminderMin` skipped on a step minute; who is told is SQL (`engine_fire_step` / `engine_remind`). INC-0142 / INC-0139 cases in `escalation.test.ts`.

Still to build here, by slice (`docs/implementation-plan.md`): L2–L3 + on-call → **S10**; client-update track wiring → **S11**; SSL / domain thresholds → **S13**.

Contract notes for the engine cron route:

- Evaluate the immediate recheck with `evaluateRound({ …, after: <first failing check time> })` so only fresh rechecks vote.
- `siteUptime` expects `downMinutes` already excluding minutes inside maintenance windows.
- `autoResolves` is called at recovery with minutes from when the PROBLEM was flagged (`detected_at`) to its first OK check (spec §19.6).

## Settled decisions (`docs/decisions.md` — don't change without a new decision record)

- **D-001:** blocked + verifier unavailable → PROBLEM (unverified) at once, Admin told, retried every round. No 10-min grace (the PRD says the same since rev 142).
- **D-002:** client-update track fires when Tier 1 DOWN reaches 15 min (`>=`), counted from the first failed check — escalation counts from "Confirmed down" instead.
- **D-003:** PROBLEM passes through Monitoring and Needs root cause like DOWN, and ends at Resolved (never In review / Closed).
- **D-004:** a site failing again while its incident is open re-enters the same incident (back to Acknowledged if acked, else Unacked / Escalated); escalation keeps its original clock; the 3rd change in 30 min tags `is_flapping`.

Round tests use minute-aligned timelines (probe ticks) and include a newer, still-incomplete round and split results, not just one clean round.

Every rule change needs a table-driven test built from the spec's worked examples (INC-0142 MuvMi, INC-0133 VOCA, INC-0139 ORCA). Cite the spec section in a comment. Ask `engine-reviewer` to check non-trivial changes.
