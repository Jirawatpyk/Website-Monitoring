# apps/vps-agent

Runs on the Thai VPS (4 GB) as two systemd instances, `dxt-agent@staging` and `dxt-agent@production` (D-019, `deploy/dxt-agent@.service`), each from its own release in `/opt/dxt-agent/<instance>/` (S04b). Release with `deploy/release.sh staging|production` — it restarts only that instance; first install in `deploy/install.md`. Two jobs: the Bangkok probe loop (every minute) and the Playwright browser verifier.

- Talks **only** to the web app's `/api/ingest` and `/api/jobs` with `INGEST_TOKEN`. It never gets a database key (PRD §10).
- HTTP checks use `runHttpCheck` from `@dxt/probe` so Bangkok judges responses exactly like Singapore and Tokyo.
- `src/probe-loop.ts`: on the UTC minute, `GET /api/ingest` for the due monitors, check them with the WAF header and each monitor's keywords (the final URL and keyword result go in the batch, S04a; a server that doesn't list keywords means none), post attempt 1 at the round's start, recheck failures ~30 s later and post attempt 2. Each round also checks the control URLs (`CONTROL_URLS`, default Google + Cloudflare; S05b, D-027) and sends `control: { ok, akamaiOk }` with each post (each batch runs its own check) — `ok` is false only when every control URL failed, so Bangkok's results can't decide a site behind a WAF that round; `akamaiOk` is the Akamai control (`AKAMAI_CONTROL_URL`, default IBM's robots.txt on Akamai NetStorage; D-027 rule 2b). A blocked result carries its WAF signature (`waf`). The server stamps Bangkok's heartbeat; the engine expects BKK only while it beats (D-019).
- D-051: the loop asks `GET /api/ingest?confirm=1`, so the server may list a Tier 2–3 home page as a confirm check (`confirm: true`); the agent posts it and its recheck with `confirm: true`. An agent without this never gets one. Deploy the web app first, then `release.sh`.
- `src/verifier.ts`: polls `GET /api/jobs` every 5 s (each poll is the verifier's heartbeat — 2 min silent = unavailable), at most `VERIFIER_MAX_SESSIONS` pages at once, plain Chromium (no stealth plugin, `src/browser.ts`), a fresh context per visit, 20 s per page (a browser challenge gets the rest of the 20 s). Verdicts: `loaded` (< 400 and every keyword), `blocked` (a WAF / challenge page in the browser too, `hasChallengeSignature` like the probes — PROBLEM, D-020), `failed` (DOWN). The JPEG goes to the signed upload URL that came with the lease; the server sets the path, the agent holds no Storage key. A verdict after the lease (60 s) is refused (409). Since S05 the probe loop sends a monitor's custom headers on every check (`probeRequestHeaders`: refused names dropped, the secret header wins, own origin only); the browser verifier doesn't send them — Playwright would carry them across redirects to another host (security review, D-025).
- `deploy/package.json` is what each `/opt/dxt-agent/<instance>/` installs next to `dist/` (Playwright only); a test keeps its version equal to this package's.
- The unit sets `UV_THREADPOOL_SIZE=16` (a test keeps it): a round starts every due check at once (`Promise.all`, 20–39 checks), each with a `getaddrinfo` per hop on libuv's pool (two until D-040 — the SSRF guard now resolves inside the connection) — at the default 4 they queued and inflated BKK's TTFB, which the response time includes (D-039). Measure on the VPS before changing the slow rules: compare BKK by minute (Tier 2 minutes are multiples of 3) and TTFB vs body.
- Pings Healthchecks.io: `HEALTHCHECKS_PING_URL_PROBE_BKK` after every probe round, `HEALTHCHECKS_PING_URL_VERIFIER` once a minute; a missed ping > 3 min emails Tao only (spec §15.3).
- `src/index.ts` (loops, signals) and `src/browser.ts` (Playwright glue) are left out of coverage; the logic around them is tested with a fake API and browser.
- `pnpm dev:agent` runs with `tsx watch`; `pnpm --filter @dxt/vps-agent build` bundles with tsup (workspace packages inlined).
