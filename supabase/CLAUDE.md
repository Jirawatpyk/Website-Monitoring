# supabase

Local stack: `pnpm db:start` (Docker). Migrations in `migrations/`, applied in filename order; `pnpm db:reset` rebuilds from scratch and runs `seed.sql`.

- One concern per migration: `pnpm exec supabase migration new <name>`. Never edit a migration that has been pushed; add a new one.
- Every table: `id uuid primary key default gen_random_uuid()`, `created_at`, `updated_at` (trigger), **RLS enabled in the same migration** with policies per role (PRD §3): admin all; responder own sites (+ Tier 1 while on call); stakeholder read + client updates for own clients; viewer read-only.
- Enums mirror `packages/shared/src/domain.ts` — change both together.
- `check_results`: monthly partitions in the `private` schema (never reachable except through the parent and its RLS), created and dropped (90 days) by `private.manage_check_results_partitions()` on a nightly pg_cron job, which also sets `autosummarize = on` on each partition's BRIN index (`check_results_checked_at_brin`'s children — Postgres refuses it on the partitioned parent), and `private.summarize_check_results_brin()` (nightly job `check-results-brin-summarize`) summarizes what autosummarize missed; `check_rollups` kept 2 years; `audit_log` append-only (no UPDATE/DELETE policies, revoke from `authenticated`).
- Every table's policies get pgTAP tests in `supabase/tests/` (`pnpm exec supabase test db`): allowed and refused access per role.
- After a schema change run `pnpm db:types` and commit `packages/db/src/database.types.ts`.
- `seed.sql` is dev sample data from the design spec; never production data.
- `auto_expose_new_tables = false`: every new table needs explicit `grant … to authenticated` (and RLS) or the API can't see it.
- Sign-up is limited by the `before_user_created` hook (D-007): the domain must be in `private.allowed_email_domains` **and** the exact lower-cased address in `private.allowed_emails (email, role)`; with no row, nobody can sign up. The first sign-in creates `profiles` with the allowlisted role (`private.handle_new_user`). Admins edit the list per environment with `access/allowlist.template.sql` (placeholders only — real addresses are inserted in each database and never committed). Hosted projects also need Auth → Hooks → `before_user_created` → `public.hook_before_user_created`, and the Google provider on; `config.toml` covers only the local stack.
- RLS helpers: `current_app_role()` (null without an active profile), `is_staff()`, `owns_site(site_id)`, `my_access()`. In policies wrap the row-independent ones as `(select public.is_staff())` / `(select public.current_app_role()) = 'admin'` so Postgres runs them once per statement, not per row (`owns_site(id)` stays per row); every change writes its own `audit_log` row inside the function that makes it (`write_audit` was dropped in S15: any session could forge a row). Signed-in sessions can't UPDATE `profiles` either since S15 (it wrote no audit row); people change only through S16's audited functions. Nobody writes the mute fields directly any more — only `mute_site` and the other window RPCs (trigger `sites_guard_update`, D-012 as amended by D-036).
- Accounts come from Google only (`private.is_trusted_sign_up`): the hook refuses, and `handle_new_user` gives no profile to, any other provider — except the reserved `.test` domain used by the local seed and tests. Keep each hosted project's Email provider off anyway.
- Deleting is restricted on purpose: a profile that owns a site, is a client's AM or has audit history can't be deleted (deactivate instead); a site with monitors or a client with sites can't be deleted by accident. Revisit if an erasure request ever needs a hard delete.
- `private.allowed_emails` is keyed by the address and has no `id` / `updated_at`: a private lookup, edited only through the template.
- Functions the service role calls (`engine_*`, `claim_notifications`, …) run as the invoker and can't reach the `private` schema: keep their SQL inline. A read function with optional filters (a keyset cursor) is plpgsql `return query execute … using`: a `language sql` function with `set search_path` isn't inlined and gets one generic plan that can't use the index (S04b `engine_checks`). pgTAP runs as `postgres` and won't notice — the integration tests (`pnpm --filter @dxt/web test:int`) will. A guard that compares a time the runner passed in (a JS Date: milliseconds) with a column SQL wrote (`now()`: microseconds) truncates the column first (`date_trunc('milliseconds', …)`), or an exact boundary is refused forever (retro S11).
- PostgREST answers at most 1,000 rows (`max_rows`), silently: a set-returning read RPC returns at most one row per entity (sites, monitors — aggregate buckets into arrays, as `overview_response_24h`), or its caller pages with `fetchAllPages` (retro S06, S06b).
- pgTAP: `pnpm db:test`; each file starts with `begin; \ir _helpers.psql` (`tests.create_user`, `tests.authenticate_as`, `tests.as_anon`) and ends with `rollback`. A new table with a foreign key to `incidents` or `sites` is emptied in `tests.clear_sites()` in the same PR, before the rows it references, or pgTAP fails on a local stack that e2e has used (retro S12b, `hand_checks`).
- "2-step" is Google Workspace 2-Step Verification, enforced by Workspace (D-007) — not Supabase MFA, and the app never reads or enforces it.
- Hosted projects (`docs/workflow.md` → Environments): **staging** only through `pnpm db:push:staging` / `pnpm db:reset:staging` (connection string from `.env.staging.local`, template `scripts/db-staging.env.example`; they refuse the production project). **Production** only through the CI job `migrate-production` on `main`. Never run `supabase link`, and never run `supabase db push` / `db reset` against a hosted project by hand — `.claude/settings.json` denies both.
- Monitoring tables (S02a) are written only by the service role; people only read (`is_staff()`; `notifications` Admin-only). Engine writes that must happen together go through `engine_open_incident` / `engine_recover_incident` / `engine_settle_incident` / `engine_record_round` (engine runs overlap since S02b — a probe whose recheck failed runs one — so `site_status` never moves back to an older round) (one transaction each, `service_role` only); the notifier claims messages with `claim_notifications(channel, limit, incident?)` (`for update skip locked` + 90 s lease; a row waits while an older one of the same incident / channel / person is queued, so a thread stays in order; the notifier sets the backoff in `next_retry_at` after a failure, or hands an unsent row back) and logs each attempt in `notification_attempts` (append-only by convention like `audit_log`: `at`, no `updated_at`; delivery records are kept, no retention job). One open incident per site (`incidents_one_open_per_site`) and one live (non-cancelled) message per incident / channel / template / person keep repeated engine runs harmless and let ack → Undo → ack queue fresh messages. S02b: the engine functions also queue per-person email (DOWN to the primary owner, RECOVERED to everyone already emailed); `queue_fallback_emails` (service role) emails a failed Chat alert to the active backup and Admins, never for a DOWN the incident has moved past; email rows go only to active profiles; `ack_incident` / `undo_ack` (`authenticated`, security definer) are the only way people change an incident so far — Admin anywhere, Responder on own sites (D-016), ACKNOWLEDGED held 10 s in `hold_until`, Undo refused once the window closed or the notifier claimed a message. The 0001 enum `site_status` is renamed `site_state` so the table can use the PRD name.
- S03 (D-019, D-020): `verification_jobs` is the verifier's queue — `claim_verification_jobs` (SKIP LOCKED, 60 s lease), `complete_verification_job` (only while the lease holds; an evidence screenshot joins the timeline), `expire_verification_jobs`; one verify job per monitor and round, one evidence job per incident (`engine_open_incident` queues it for a hard-fail DOWN, or links the verify job when the browser decided). `agent_heartbeats` (the verifier's last poll), `engine_note_site` (the site note of the latest judged round). `system_alerts` holds Admin alerts that aren't about one incident: `open_system_alert` opens one per kind and queues an email per active Admin in the same transaction, `clear_system_alert`; `notifications` names an incident or a system alert (exactly one). Private bucket `verifier-screenshots` (JPEG ≤ 1 MB, no policies — signed URLs only). BKK is active; the engine expects a location only while it beats. `engine_escalate_incident` raises an open PROBLEM to DOWN and queues its DOWN alert (D-021). `tests.clear_sites()` also empties the jobs and alerts.
- S04a (D-022): `check_results` keeps `final_url`, `keyword_missing`, `keyword_forbidden` (null = not checked). `monitor_status` (one row per monitor, staff read, service-role write) holds the engine's carry state — last verdict, trigger and cause, slow streak, per-location failing-since — written only through `engine_write_monitors`, which every `engine_*` function calls with its optional `p_monitors` / `p_status` in the same transaction (a monitor row never moves back or counts a round twice). `system_alerts.kind` adds `probe_locations_low`.
- S04b (D-024): `engine_relapse_incident` joins a new drop to a recovered incident (state-guarded; Acknowledged / Escalated / Unacked; severity only up; DOWN AGAIN / PROBLEM AGAIN Chat reply); `incidents.episode_severity` (the drop in progress) and `auto_resolved`; `site_status.flips` / `flip_ok` written by `engine_record_flip` inside the engine functions; `engine_recover_incident` takes `p_flip_ok`, `p_auto_resolve` (→ Resolved, PROBLEM never acked only) and `p_hold_summary` (a `flap_summary` held 15 min instead of RECOVERED; `engine_cancel_flap_summary` on any new drop); `notifications.dedupe_key` joins `notifications_once_per_incident`, so RECOVERED / AGAIN / summary repeat per round (the fallback email keeps the key). Read RPCs for the engine: `engine_checks` (keyset on checked_at, id), `engine_monitor_status`, `engine_verify_jobs` — active sites only, service role only.
- S05 (D-025): every insert / update / delete on `sites`, `monitors` and `clients` writes one `audit_log` row (trigger `private.audit_row_change`, actor = the signed-in person or null for a script; a no-op update writes nothing). Signed-in writes (the session's `role` setting is `authenticated`, not JWT claims) must name owners who are active Admins / Responders with a Google Chat id (`sites_require_linked_owners`, after D-012's guard), and a live site (`is_active`) must stay complete — checked at commit by deferred constraint triggers through `private.site_start_problems` (pgTAP fires them with `set constraints all immediate`, see `pg_temp.run` in `sites_registration.test.sql`). The UI writes through `create_site` / `update_site` / `set_site_monitoring` / `save_monitors` / `delete_site` (security invoker, Admin only). A Draft = `is_active = false`; a monitor with history is soft-removed (`removed_at`, `enabled = false`) and probes / the engine skip it. One site per primary URL (`monitors_primary_url_key`). A Chat id is digits only (`profiles_google_chat_user_id_digits`, `not valid` on old rows). Clients / AMs and Chat ids per environment: `access/clients.template.sql`, `access/chat-ids.template.sql`.
- `check_results` is the big partitioned table: a new CHECK or FK on it goes in `not valid`, and `alter table … validate constraint` goes in the **next** migration file (each file is one transaction: validating in the same file holds the ACCESS EXCLUSIVE lock through the scan), with `set local lock_timeout = '5s'` at the top of each; new columns nullable without a default (catalog-only).
- S05b (D-027, D-028): `check_results.waf` (a blocked check's header-level WAF signature, text + check like `location` — mirrors `WAF_VENDORS`) and `control_ok` (BKK only: the VPS's control check for that batch), `akamai_ok` (BKK only: its Akamai control, D-027 rule 2b); `system_alerts.kind` adds `bkk_control_failing`. A new `check_results` column also goes into `LAG_TOLERANT_COLUMNS` (`apps/web/src/server/check-results.ts`) or its core list — a deploy's crons run before `migrate-production` (`docs/workflow.md`), and a test fails until it is classified. - S07 (D-033): people also change an incident through `add_incident_note` (event + Chat NOTE at once, `dedupe_key` = event id), `save_root_cause` (any time before Resolved; the nine categories in `incidents_root_cause_category_check`, mirrored by `ROOT_CAUSE_CATEGORIES`), `resolve_incident` (the three conditions checked in SQL: an `ok_two_rounds` event since `recovered_at`, the client update not required or marked, a category other than `unknown`; RESOLVED held 10 s to Chat and everyone already emailed; a held flap summary set aside) and `undo_resolve` (own resolve, inside 10 s, back to the state it came from) — same `private.can_ack` rule as ack. `engine_settle_incident` writes `ok_two_rounds` on every settle; `engine_relapse_incident` refuses a DOWN on a PROBLEM incident (that is `engine_escalate_incident`).
- S08 (D-034): `escalation_policies` (Tier 1 / 2 / 3 DOWN, PROBLEM · all tiers) and `escalation_steps` (level, delay, role tokens `owner` / `backup` / `admins` / `site_am` / `ceo`, channels `chat` / `space` / `email` / `voice`), `organisation_settings` (one row: Tier 2–3 response hours, reminder intervals) and `company_holidays` (audited by trigger) — staff read, the Admin writes only through `save_escalation_policies` (every guardrail again, one `escalation.update` audit row with the note). `incidents.escalation_plan` keeps the policy an incident opened with (`escalation_plan_for`; D-021 swaps in the DOWN policy and resets the level when nobody acked; incidents before S08 have none and never escalate). The ladder's writes, service role only: `engine_fire_step` (Unacked / Escalated, level not yet fired, the thread's first alert out — `engine_thread_live`; the step's people minus anyone told, an Admin beside someone new is FYI; Escalated only when someone new was told; `step_fired` event; Chat + email keyed `<severity>:L<n>`) and `engine_remind` (Chat only, keyed by severity + due minute). A Tier 2–3 PROBLEM or PROBLEM AGAIN outside response hours is queued with `hold_until` (`p_hold_until` on open / relapse), never blocks its thread, and is cancelled (`engine_cancel_held_problem`) on recovery, D-021 or an ack (Undo restores it); RECOVERED goes only when an alert really went. An ack or a recovery sets aside a step or reminder still waiting (`engine_cancel_ladder`); `queue_fallback_emails` never emails a reminder.
- S09 (D-036 as amended, spec §23): `maintenance_windows` holds maintenance windows and mutes (`kind`); staff read, nobody writes directly. People use `create_maintenance` / `mute_site` / `end_window_early` / `edit_window_end` / `cancel_window` (Acknowledge rule, `private.can_pause`), `withdraw_request` (the asker or the site's owner / backup, never an Admin), `approve_maintenance` / `decline_maintenance` (Admin) — security definer, a reason every time (`private.require_reason`), one audit row (§23.11 names: maintenance.request / create / approve / decline / withdraw / edit / cancel / start / end / end_early, site.mute / mute_end) and one `log` line (`private.window_log`, never replaced) in the same transaction. `window_state(w, at)` = waiting / scheduled / active / ended / cancelled / withdrawn / declined / not_approved / didnt_start (`outcome` holds the last four; mirrored by `windowState` in `@dxt/engine`). A mute starts now, ≤ 24 h from its start, one at a time, never during the site's maintenance, and mirrors itself into `sites.muted_until` / `mute_reason` / `muted_at` (writers set `dxt.window_write` so the row-change audit stays quiet; a direct write from a signed-in session is refused — `current_user = 'authenticated'`; a muted insert too). Maintenance: not now on a site that is DOWN or has an incident that hasn't recovered (`private.site_busy`: unacked / escalated / acknowledged), one per site at a time (`private.assert_no_overlap`, detail "<site>|<start>|<end>"), an end ≥ 5 min away (`private.assert_end`), over 24 h (chained, `private.chained_minutes`) waits for an Admin unless an Admin made it; starting ends a running mute. Engine, service role: `engine_log_windows` (unapproved at start → not_approved; a start on a busy site → didnt_start; else maintenance.start and the mute ends; ran its course → maintenance.end / site.mute_end; clears mute rows with no running mute), `engine_silent_incidents` + `engine_post_late_alert` (an incident a mute silenced gets its first alert once the mute is over; `incidents.alerted_at` restarts its ladder clock; `engine_thread_live` / `engine_fire_step` / `engine_remind` count only the current drop's alert and never fire a level due before `alerted_at`).
- S09b (D-037, spec §24): `notifications` names an incident, a system alert **or a maintenance window** (`maintenance_window_id`, exactly one; `notifications_once_per_window` adds `dedupe_key`). `engine_queue_window_messages(window, kind, actor, hold, key, extra)` (security definer, service role + the RPCs) queues one action's messages: the `mw_line` in the window's Space thread (`thread_key` `mw-<id>`), `mw_dm` replies @mentioning each person a DM would reach (`context.dm`; no Chat app yet), `mw_email` per owner / backup (+ Admins in a request thread; `context.role`), minus the actor, active people only; mutes and the 1 h reminder are Chat only; a mute on a site with an open incident whose thread exists adds a `muted` line there. The six undoable actions (approve, decline, end now, edit end, cancel, withdraw) save the window with `private.window_undo_begin` and hold their rows 10 s; `undo_window_action` (the actor, inside 10 s, nothing claimed) restores it, cancels the rows (`error = 'Undone'`), adds a log line and `maintenance.undo`. `engine_log_windows` queues started / ended / mute_ended / didnt_start / not_approved; `engine_window_reminders` the 12 h / 1 h reminders (stamped `reminded_12h_at` / `reminded_1h_at`); `engine_silent_incidents` waits out a person-ended mute's Undo; the late alert's context carries `heldUntil`. `maintenance_windows` is in the Realtime publication.

- S11 (FR-20, D-052, spec §9, §16.6):
  - **When it fires:** the runner calls `engine_client_update_due(incident, due_at, context)` (service role) once the track is due. The due time comes from `@dxt/engine`; SQL never works out hours.
  - **What it checks:** the incident is DOWN and still open (a recovered one counts), the site is Tier 1–2, the client isn't internal, `due_at` ≥ `started_at` + 15 min (at millisecond precision), and the thread has a live DOWN / DOWN AGAIN Chat row from any drop (T09: a muted site keeps it). Not `engine_thread_live`, which looks for the current drop's severity, so a held PROBLEM AGAIN would hold the track back.
  - **What it writes:** `client_update_required` / `client_update_due_at`; a Chat reply in the thread @mentioning the active AM, or the Admins with `noAm`; an email to each of them (`dedupe_key` `client_update`); the `client_update_due` event stamped at `due_at`; and `incident.client_update_due` in the audit log. Fired on an incident already in Monitoring / Needs root cause after a DOWN drop: that recovery's RECOVERED email to the same people, copied from its Chat reply and stamped after the client-update email (D-052 item 7). Never for a PROBLEM drop (D-038).
  - **Marking:** people use `mark_client_update(incident, not_needed, note)`, guarded by `private.can_client_update`: an Admin, a Responder on own sites (not on call), or the client's AM (Stakeholder or Responder).
