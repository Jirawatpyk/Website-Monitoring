# supabase

Local stack: `pnpm db:start` (Docker). Migrations in `migrations/`, applied in filename order; `pnpm db:reset` rebuilds from scratch and runs `seed.sql`.

- One concern per migration: `pnpm exec supabase migration new <name>`. Never edit a migration that has been pushed; add a new one.
- Every table: `id uuid primary key default gen_random_uuid()`, `created_at`, `updated_at` (trigger), **RLS enabled in the same migration** with policies per role (PRD §3): admin all; responder own sites (+ Tier 1 while on call); stakeholder read + client updates for own clients; viewer read-only.
- Enums mirror `packages/shared/src/domain.ts` — change both together.
- `check_results`: monthly partitions in the `private` schema (never reachable except through the parent and its RLS), created and dropped (90 days) by `private.manage_check_results_partitions()` on a nightly pg_cron job; `check_rollups` kept 2 years; `audit_log` append-only (no UPDATE/DELETE policies, revoke from `authenticated`).
- Every table's policies get pgTAP tests in `supabase/tests/` (`pnpm exec supabase test db`): allowed and refused access per role.
- After a schema change run `pnpm db:types` and commit `packages/db/src/database.types.ts`.
- `seed.sql` is dev sample data from the design spec; never production data.
- `auto_expose_new_tables = false`: every new table needs explicit `grant … to authenticated` (and RLS) or the API can't see it.
- Sign-up is limited by the `before_user_created` hook (D-007): the domain must be in `private.allowed_email_domains` **and** the exact lower-cased address in `private.allowed_emails (email, role)`; with no row, nobody can sign up. The first sign-in creates `profiles` with the allowlisted role (`private.handle_new_user`). Admins edit the list per environment with `access/allowlist.template.sql` (placeholders only — real addresses are inserted in each database and never committed). Hosted projects also need Auth → Hooks → `before_user_created` → `public.hook_before_user_created`, and the Google provider on; `config.toml` covers only the local stack.
- RLS helpers: `current_app_role()` (null without an active profile), `is_staff()`, `owns_site(site_id)`, `my_access()`. In policies wrap the row-independent ones as `(select public.is_staff())` / `(select public.current_app_role()) = 'admin'` so Postgres runs them once per statement, not per row (`owns_site(id)` stays per row); audit rows through `write_audit(...)`. A Responder may change only the mute fields of own sites (trigger `sites_guard_update`, D-012).
- Accounts come from Google only (`private.is_trusted_sign_up`): the hook refuses, and `handle_new_user` gives no profile to, any other provider — except the reserved `.test` domain used by the local seed and tests. Keep each hosted project's Email provider off anyway.
- Deleting is restricted on purpose: a profile that owns a site, is a client's AM or has audit history can't be deleted (deactivate instead); a site with monitors or a client with sites can't be deleted by accident. Revisit if an erasure request ever needs a hard delete.
- `private.allowed_emails` is keyed by the address and has no `id` / `updated_at`: a private lookup, edited only through the template.
- Functions the service role calls (`engine_*`, `claim_notifications`, …) run as the invoker and can't reach the `private` schema: keep their SQL inline. pgTAP runs as `postgres` and won't notice — the integration tests (`pnpm --filter @dxt/web test:int`) will.
- pgTAP: `pnpm db:test`; each file starts with `begin; \ir _helpers.psql` (`tests.create_user`, `tests.authenticate_as`, `tests.as_anon`) and ends with `rollback`.
- "2-step" is Google Workspace 2-Step Verification, enforced by Workspace (D-007) — not Supabase MFA, and the app never reads or enforces it.
- Hosted projects (`docs/workflow.md` → Environments): **staging** only through `pnpm db:push:staging` / `pnpm db:reset:staging` (connection string from `.env.staging.local`, template `scripts/db-staging.env.example`; they refuse the production project). **Production** only through the CI job `migrate-production` on `main`. Never run `supabase link`, and never run `supabase db push` / `db reset` against a hosted project by hand — `.claude/settings.json` denies both.
- Monitoring tables (S02a) are written only by the service role; people only read (`is_staff()`; `notifications` Admin-only). Engine writes that must happen together go through `engine_open_incident` / `engine_recover_incident` / `engine_settle_incident` / `engine_record_round` (engine runs overlap since S02b — a probe whose recheck failed runs one — so `site_status` never moves back to an older round) (one transaction each, `service_role` only); the notifier claims messages with `claim_notifications(channel, limit, incident?)` (`for update skip locked` + 90 s lease; a row waits while an older one of the same incident / channel / person is queued, so a thread stays in order; the notifier sets the backoff in `next_retry_at` after a failure, or hands an unsent row back) and logs each attempt in `notification_attempts` (append-only by convention like `audit_log`: `at`, no `updated_at`; delivery records are kept, no retention job). One open incident per site (`incidents_one_open_per_site`) and one live (non-cancelled) message per incident / channel / template / person keep repeated engine runs harmless and let ack → Undo → ack queue fresh messages. S02b: the engine functions also queue per-person email (DOWN to the primary owner, RECOVERED to everyone already emailed); `queue_fallback_emails` (service role) emails a failed Chat alert to the active backup and Admins, never for a DOWN the incident has moved past; email rows go only to active profiles; `ack_incident` / `undo_ack` (`authenticated`, security definer) are the only way people change an incident so far — Admin anywhere, Responder on own sites (D-016), ACKNOWLEDGED held 10 s in `hold_until`, Undo refused once the window closed or the notifier claimed a message. The 0001 enum `site_status` is renamed `site_state` so the table can use the PRD name.
- S03 (D-019, D-020): `verification_jobs` is the verifier's queue — `claim_verification_jobs` (SKIP LOCKED, 60 s lease), `complete_verification_job` (only while the lease holds; an evidence screenshot joins the timeline), `expire_verification_jobs`; one verify job per monitor and round, one evidence job per incident (`engine_open_incident` queues it for a hard-fail DOWN, or links the verify job when the browser decided). `agent_heartbeats` (the verifier's last poll), `engine_note_site` (the site note of the latest judged round). `system_alerts` holds Admin alerts that aren't about one incident: `open_system_alert` opens one per kind and queues an email per active Admin in the same transaction, `clear_system_alert`; `notifications` names an incident or a system alert (exactly one). Private bucket `verifier-screenshots` (JPEG ≤ 1 MB, no policies — signed URLs only). BKK is active; the engine expects a location only while it beats. `tests.clear_sites()` also empties the jobs and alerts.
- Staging test monitor: `staging/test-target.sql` (placeholders only, staging only) adds the "Test target" site and primary monitor pointing at `apps/test-target`; staging resets don't seed, so run it again after `pnpm db:reset:staging`. `staging/reset-test-incident.sql` resolves its open incident before a repeat DOWN test (needed until S04 / S07).
